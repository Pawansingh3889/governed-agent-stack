Governed Agent Stack
architecture

Thirteen declared components for pointing an agent at a regulated database and being able to prove afterwards what it touched. Every one of them is checked against the stack’s own governance bar before it ships.

Components 13 declared in stack.yaml Licences allowed MIT, Apache-2.0 Self-check make check
The move that makes this more than a toolbox

The stack governs itself with the same kind of policy it helps you apply to an agent. The components are declared as data in stack.yaml; policies/stack.rego fails the build if any of them has no licence, a licence outside the allowed set, no source repo, on_prem unset, or a governance role that is not a recognised concern.

What a question passes through

Two postures, and what changes between them

Compose the pieces and the model writes SQL that gates then validate. Use sql-steward and the model never writes SQL at all, so there is nothing to validate and no run_sql tool to misuse.

Self-check

How the stack holds itself to the bar

Policy as code

Declared, not described

Components live in stack.yaml as machine-readable data. Adding one means it must pass the same check as everything already there, so the register cannot quietly drift from the rules.

Deny rules

Five ways to fail the check

No licence, a licence outside MIT or Apache-2.0, on_prem unset, no source repo, or a role outside the twelve recognised governance concerns. Any one of them fails make policy.

One command

make check

Runs the governance policies against the register and validates control-tower’s registry against the actual checkout, so what the console claims is installed and what is installed cannot disagree.
